# LORIS security hardening package

This consolidated workspace includes the security-hardening pass for the supplied Group B R2 API. It does not execute database migrations and does not contain production credentials.

## Implemented in source

- Group B R2 API verifies each bearer access token by calling the Supabase Auth `/auth/v1/user` endpoint. It does not trust a user ID supplied by the browser.
- Upload and delete operations require an authenticated user and an active `admin` membership for the target organisation, or the `platform_manager` platform role.
- Organisation membership checks correctly translate `Memberships.user_id` through `Profiles.id`; they do not confuse it with `auth.users.id`.
- CORS is allow-list based and fails closed for unlisted browser origins.
- Per-IP rate limits are applied to upload and delete endpoints. The included in-memory limiter is suitable for a single server process only; use a shared Redis-backed limiter or gateway limit when horizontally scaling.
- Uploads have a 25 MB per-file limit, bounded file/field counts, extension checks, and file-signature checks for PDF, EPUB, MP3, MP4, JPEG and PNG.
- R2 object names are generated by the server and namespaced by organisation ID. User-supplied filenames are not used as object keys.
- R2 deletion now requires a material ID, checks the material's organisation ownership, and only accepts URLs already stored on that material and belonging to configured R2 public URL prefixes.
- Basic security headers, no-store caching, JSON body limits and generic error responses are enabled.

## New database migration (not executed)

`database/migrations/20261115_security_rls_and_org_ownership.sql` is an additive migration for review; it also adds the end-user `support_tickets` table required by Group C. It:

- Adds nullable `materials.organisation_id` and a foreign key to `public."Organisation"(id)`.
- Adds `organisation_requests` for organisation registration review.
- Adds security-definer permission helper functions.
- Adds an idempotent `auth.users` insert trigger to create a basic `Profiles` row for newly registered users (existing profiles are left unchanged).
- Enables RLS and defines policies for Profiles, Organisation, Memberships, organisation_requests, categories, materials, and all user-owned tables in the supplied schema.
- Uses `auth.uid()` for user-owned tables, and Profiles.id only for `Memberships.user_id`.
- Does not delete or rewrite existing rows. Existing materials remain unassigned (`organisation_id IS NULL`) until manually reviewed and backfilled.

**Do not apply the migration until it has been reviewed against the live Supabase schema, table grants, and existing policies.** RLS policies are permissive when multiple policies apply; inspect existing policies before applying this file.

## Server environment

Copy `LORIS-group-B/server/.env.example` to `.env` and fill it locally. Keep `.env` out of version control. The service-role key belongs only on the server.

The server verifies access tokens by asking Supabase Auth to validate them. This avoids embedding a JWT secret in the client or manually implementing signature verification. The service-role key is used only for server-side profile, membership and material lookups.

## Frontend integration still required

The consolidated Group B upload and material-management pages now call the hardened endpoints with the session token and organisation context. Keep these requirements in place when further changing the pages:

1. Obtain the current Supabase session and send `Authorization: Bearer <access_token>`.
2. Resolve the active organisation and send `X-Organisation-Id`.
3. Insert metadata with `uploaded_by = auth user id` and `organisation_id = selected organisation id`.
4. Include `materialId` when requesting R2 deletion.
5. Check and handle Supabase insert/update/delete errors; do not display success when a database operation fails.

The migration is designed to make direct client-side metadata writes subject to RLS. A future integration should move upload + metadata creation into one backend operation or implement compensating cleanup if metadata insertion fails, to avoid orphaned R2 objects.

## Supabase project-level controls to configure separately

These controls cannot be enabled from this source archive because they are Supabase project dashboard/auth settings:

- Configure Auth rate limits appropriate to expected traffic.
- Enable CAPTCHA for sign-up and other exposed Auth flows where supported.
- Enable leaked-password protection if available on the project plan/configuration.
- Set production redirect URLs and allowed origins; remove unused localhost URLs.
- Require email verification if it is part of the product's onboarding policy.
- Consider MFA for Platform Managers and organisation administrators.
- Review Auth email templates, password policy, session lifetime and refresh-token settings.
- Review database grants and existing RLS policies before migration.
- Ensure R2 buckets are private where appropriate. Public R2 URLs bypass database RLS; use authenticated proxy delivery or short-lived signed URLs for protected materials.

## Important limitations / verification

- No Supabase or R2 credentials were included in the archive, so no live integration was tested.
- The migration was prepared but not run.
- The in-memory rate limiter resets on restart and is not shared between multiple instances. It protects the R2 API endpoints only; configure Supabase Auth rate limits/CAPTCHA separately for sign-in and sign-up.
- The R2 server now requires `organisation_id` on material rows for delete authorisation. Existing unassigned materials are intentionally blocked from deletion through this endpoint until ownership is reviewed.
- This package is a security-focused patch to the supplied Group B server and a reviewable RLS migration. It is not the full LORIS multi-group consolidation.

## Run the hardened R2 API locally

From `LORIS-group-B/server`:

```bash
npm install
cp .env.example .env
# Fill the server-only values in .env, then:
npm run check
npm run dev
```

Set `VITE_API_BASE_URL` in the Group B frontend `.env` to the API origin. Do not put `SUPABASE_SERVICE_ROLE_KEY` or any R2 secret in the frontend environment.

The Group B upload UI resolves an active organisation-admin membership and sends the Supabase access token plus `X-Organisation-Id`. It auto-selects only when exactly one eligible organisation exists; accounts administering multiple organisations still need an organisation selector before production use. The full multi-group integration status is documented in `INTEGRATION_STATUS.md`.
